# Aave V3 primary-source research notes

Reviewed 2026-09-11. Scope: mechanics relevant to future research, not a scoring formula or a claim about the currently deployed Base market. No RPC request or application change was made for this research.

## Provenance and review boundaries

The official Aave documentation is useful for interfaces and concepts but contains mixed-version statements. Resolve behavior against the implementation deployed at a specified chain and block, together with executed governance payloads. A source branch, release note, address book, or proposal alone does not establish deployment.

The archive includes the upstream licenses: [Origin license](sources/aave/origin-LICENSE) and [price-feeds license](sources/aave/feeds-LICENSE). These are research copies, not application dependencies. Source-specific SPDX identifiers still apply; `AaveOracle.sol` is MIT, while much of the other code is BUSL-1.1. ## C. Protocol risk mechanics

### Collateral, debt, and valuation

Supplying mints aTokens; supply is not equivalent to collateral eligibility. User collateral flags and effective reserve/eMode parameters matter. Borrowing creates variable debt; credit delegation can separate the transaction sender from the account whose collateral backs the debt. Account views expose aggregate collateral, debt, borrowing headroom, effective LTV, effective liquidation threshold, and health factor. Positions must be attached to the correct account and market. [AV-P](https://aave.com/docs/aave-v3/smart-contracts/pool#borrow)

In the reviewed account-calculation implementation, only enabled collateral enters collateral valuation; borrow flags select debt. Both sides use market-oracle prices and reserve decimals. Conceptually, health factor is collateral value weighted by effective liquidation thresholds divided by debt value; this is an existing protocol calculation, not a proposed project score. The exact code computes the numerator before reducing the average threshold, so recomputation from a rounded displayed average can differ. Health factor is scaled by 10^18; no debt produces `uint256.max`, which must be interpreted as a no-debt sentinel rather than a gigantic comparable risk observation. [AV-G](https://github.com/aave-dao/aave-v3-origin/blob/8305565ae342f1773c42cd2e4593f175fe5968a0/src/contracts/protocol/libraries/logic/GenericLogic.sol)

LTV limits new borrowing; liquidation threshold determines liquidation eligibility. They are distinct. Collateral settings and liquidation bonus use basis points; 10,500 represents 105% total collateral value, hence a 5% bonus. Caps are in whole asset tokens; a zero supply or borrow cap means uncapped, not zero permitted activity. Freeze blocks new supply/borrowing while permitting exit-related operations; pause is more restrictive. Admin roles can change parameters. [AV-C](https://aave.com/docs/aave-v3/smart-contracts/pool-configurator#configurereserveascollateral)

The interest model has separate slopes below and above an optimal usage ratio. Rate inputs include debt, reserve factor, and balance accounting; quoted variable rates and liquidity rates are not fixed yields. Use the deployed strategy and its units, including ray-scaled rates, rather than historical example parameter tables. [AV-I](https://aave.com/docs/aave-v3/smart-contracts/interest-rate-strategy)

### Liquidation eligibility, quantity, and economic execution

The reviewed validation code requires health factor strictly below 1; equality is not sufficient. It additionally requires relevant reserves active/unpaused, the selected collateral enabled, nonzero selected debt, and expired per-reserve liquidation grace periods. It prohibits self-liquidation. Therefore a health-factor breach is not by itself a complete transaction-success test. [AV-V](https://github.com/aave-dao/aave-v3-origin/blob/8305565ae342f1773c42cd2e4593f175fe5968a0/src/contracts/protocol/libraries/logic/ValidationLogic.sol#L253)

The pinned liquidation implementation permits the whole selected reserve debt by default. The 50% restriction applies only when selected collateral value and selected debt value are each at least 2,000e8 base units and HF exceeds 0.95e18; that limit is measured against aggregate position debt, not 50% of each reserve. Thus an entire smaller debt reserve may be liquidated even in that restricted regime. A liquidation retaining both selected debt and collateral must leave at least 1,000e8 of each; fully clearing one side is allowed. These constants assume USD prices with eight decimals, not an arbitrary base currency. Actual collateral limits, bonus, fees, and integer rounding also bound repayment. [AV-L](https://github.com/aave-dao/aave-v3-origin/blob/8305565ae342f1773c42cd2e4593f175fe5968a0/src/contracts/protocol/libraries/logic/LiquidationLogic.sol)

V3.3 introduced position-wide close factors, size-dependent full liquidation, and dust rules. It also records newly created collateral-exhausted bad debt as reserve deficit while burning affected debt tokens, stopping that debt's future interest accrual. Burning the claim is accounting recognition, not economic recovery; historical bad-debt accounts are a separate cleanup issue. Liquidator incentives still depend on gas cost, bonus, and secondary-market liquidity. [AV-33](https://github.com/aave-dao/aave-v3-origin/blob/8305565ae342f1773c42cd2e4593f175fe5968a0/docs/3.3/Aave-v3.3-features.md)

V3.7's rounding note replaces half-up operations with explicit floor/ceiling choices for seized collateral and the fee split. Tiny residual or fee differences cannot be interpreted without the implementation version. [AV-37R](https://github.com/aave-dao/aave-v3-origin/blob/8305565ae342f1773c42cd2e4593f175fe5968a0/docs/3.7/liquidation-rounding.md)

### Isolation and eMode are version-sensitive

Legacy isolation restricts collateral to one isolated asset, allows specified borrow assets, and imposes a debt ceiling. Supplying another asset does not necessarily make it collateral. This is the mechanism described by the public isolation help page, not proof that it remains enabled on Base. [AV-ISO](https://aave.com/help/supplying/isolation-mode)

V3.6 decouples eMode collateral/borrowing configuration from ordinary reserve settings and adds an eMode-specific LTV-zero bitmap. Default reserve borrowing-disabled or LTV-zero flags alone can therefore misdescribe a particular eMode user's permissions. Received aTokens no longer automatically become collateral on ordinary transfers or liquidation receipts. [AV-36](https://github.com/aave-dao/aave-v3-origin/blob/8305565ae342f1773c42cd2e4593f175fe5968a0/docs/3.6/Aave-v3.6-features.md#emode-improvements)

V3.7 removes legacy debt-ceiling isolation and siloed borrowing. Compatibility data providers can continue returning zeros/false for deprecated fields, so zero values need not represent a live configurable safeguard. [AV-37M](https://github.com/aave-dao/aave-v3-origin/blob/8305565ae342f1773c42cd2e4593f175fe5968a0/docs/3.7/mode-removal.md)

A different V3.7 mechanism adds an isolated flag to eMode categories: assets outside its collateral bitmap contribute zero LTV, but retain their liquidation-threshold contribution when already enabled. Entry and new collateral enablement are restricted; toggling this flag need not instantly lower HF. This is not legacy isolation mode and should not be merged into one boolean. [AV-37E](https://github.com/aave-dao/aave-v3-origin/blob/8305565ae342f1773c42cd2e4593f175fe5968a0/docs/3.7/isolated-emode.md)

## D. Oracle risk mechanics

AaveOracle exposes asset-source and fallback configuration. The historical sentinel introduces an L2 sequencer recovery grace period for borrowing/liquidations; this is distinct from price-feed freshness. Admin-configured sources can change. [AV-O](https://aave.com/docs/aave-v3/smart-contracts/oracles)

The pinned AaveOracle returns the configured base-currency unit for its base asset, delegates missing sources to fallback, and accepts a source's positive `latestAnswer()`. Nonpositive answers invoke fallback. It does not itself read update timestamps, enforce heartbeats, or catch a reverting source call. Consequently a positive stale answer does not automatically trigger fallback here, and an upstream revert can propagate. The fallback address's existence does not prove it is functional or independent; inspect its actual deployment and implementation. [AV-OC](https://github.com/aave-dao/aave-v3-origin/blob/8305565ae342f1773c42cd2e4593f175fe5968a0/src/contracts/misc/AaveOracle.sol#L103)

Aave's source may be an adapter rather than a direct Chainlink feed: ratio-capped LST pricing, fixed-upper-cap stablecoins, composed pairs, fixed prices, and maturity-dependent PT transforms exist. Map the full dependency chain from reserve to Aave source to all underlying feeds or ratio providers. [AV-F](https://github.com/aave-dao/aave-price-feeds/blob/00d0f14b0734dc6faf41960bb9023c0b742a944b/README.md)

The stable adapter returns the lower of a positive upstream answer and its configured upper cap; nonpositive values become zero. An upper cap does not floor a depeg at one dollar. Changes are role-controlled, and `isCapped()` exposes current cap engagement. [AV-FS](https://github.com/aave-dao/aave-price-feeds/blob/00d0f14b0734dc6faf41960bb9023c0b742a944b/src/contracts/PriceCapAdapterStable.sol)

The LST base adapter multiplies the underlying price by a ratio bounded using snapshot ratio, elapsed time, and maximum growth. Nonpositive ratio/base price returns zero. Snapshot timestamps must advance and fall within the allowed age window when updating parameters. The 180-day maximum is enforced at parameter-setting time; the reviewed price-read function does not automatically fail once an existing snapshot becomes older than 180 days. Neither capped adapter checks feed timestamps in its shown price-read function. [AV-FB](https://github.com/aave-dao/aave-price-feeds/blob/00d0f14b0734dc6faf41960bb9023c0b742a944b/src/contracts/PriceCapAdapterBase.sol)

Composition requires unit and decimal checks. Some composed adapters perform no cap; CAPO administration also depends on parameter maintenance, not merely cryptographic feed authenticity. The adapter documentation explicitly distinguishes basic validation from additional steward controls. [AV-FD](https://github.com/aave-dao/aave-price-feeds/blob/00d0f14b0734dc6faf41960bb9023c0b742a944b/src/contracts/README.md)

V3.7 removes sequencer-sentinel checks from borrow/liquidation validation. The preceding behavior had an HF-below-0.95 liquidation exception even when the sentinel blocked other liquidations. The 0.95 sentinel exception used a strict inequality; it is distinct from the inclusive full-close-factor boundary. Per-reserve liquidation grace periods remain in the reviewed validation code. Do not infer any Base protection from the historical oracle-doc page without identifying deployed code. [AV-37S](https://github.com/aave-dao/aave-v3-origin/blob/8305565ae342f1773c42cd2e4593f175fe5968a0/docs/3.7/sentinel-removal.md)

## F. Things that should not be scoring signals

- Aave branding, a listing, a Chainlink label, eMode membership, or existence of fallback configuration as an unconditional safety guarantee. These describe architecture or permissions. [AV-P](https://aave.com/docs/aave-v3/smart-contracts/pool), [AV-OC](https://github.com/aave-dao/aave-v3-origin/blob/8305565ae342f1773c42cd2e4593f175fe5968a0/src/contracts/misc/AaveOracle.sol)
- A universal safe HF, or HF above one as absence of protocol/oracle risk. The official help text explicitly rejects one universally safe HF. [AV-H](https://aave.com/help/borrowing/liquidations)
- The latest repository version as the deployed Base version; a governance proposal as executed state; legacy zero-filled fields as operative controls. [AV-AB](https://github.com/aave-dao/aave-address-book/blob/main/src/AaveV3Base.sol), [AV-37M](https://github.com/aave-dao/aave-v3-origin/blob/8305565ae342f1773c42cd2e4593f175fe5968a0/docs/3.7/mode-removal.md)
- An upper stablecoin price cap as downside peg insurance; absence of a timestamp on an adapter as evidence its dependencies are fresh. [AV-FS](https://github.com/aave-dao/aave-price-feeds/blob/00d0f14b0734dc6faf41960bb9023c0b742a944b/src/contracts/PriceCapAdapterStable.sol), [AV-FB](https://github.com/aave-dao/aave-price-feeds/blob/00d0f14b0734dc6faf41960bb9023c0b742a944b/src/contracts/PriceCapAdapterBase.sol)
- Missing data silently converted to zero risk; no-debt sentinel treated as numerical HF; APY treated as guaranteed return. [AV-G](https://github.com/aave-dao/aave-v3-origin/blob/8305565ae342f1773c42cd2e4593f175fe5968a0/src/contracts/protocol/libraries/logic/GenericLogic.sol), [AV-I](https://aave.com/docs/aave-v3/smart-contracts/interest-rate-strategy)

These exclusions are methodology guardrails inferred from the documented mechanics, not an Aave-prescribed scoring scheme.

## Conflicts and missing evidence before scoring

1. **Liquidation documentation conflict:** the Pool page says liquidation is limited to 50% and implies HF is restored above one. The help page and newer implementation permit full selected-debt liquidation in qualifying cases; collateral-exhaustion deficit handling disproves an unconditional recovery guarantee. Do not reuse the Pool prose as an executable specification. [AV-P](https://aave.com/docs/aave-v3/smart-contracts/pool#liquidationcall), [AV-H](https://aave.com/help/borrowing/liquidations), [AV-33](https://github.com/aave-dao/aave-v3-origin/blob/8305565ae342f1773c42cd2e4593f175fe5968a0/docs/3.3/Aave-v3.3-features.md)
2. **Mixed-version oracle/mode documentation:** web docs retain sentinel and legacy isolation behavior removed by V3.7 sources. Some V3.7 narrative retains references to old interfaces. Resolve the exact Base implementation and contract call sites at a fixed block; do not translate documentation omissions into security claims. [AV-O](https://aave.com/docs/aave-v3/smart-contracts/oracles), [AV-37S](https://github.com/aave-dao/aave-v3-origin/blob/8305565ae342f1773c42cd2e4593f175fe5968a0/docs/3.7/sentinel-removal.md)
3. **Base state is not collected:** gather official address-book revision, deployed verified source/bytecode, proxy implementations, executed upgrade and parameter payloads/events, ACL holders and steward permissions, reserves, modes, deficits, oracle sources/adapters/fallbacks, relevant feed configuration. Start with the [official Base address book](https://github.com/aave-dao/aave-address-book/blob/main/src/AaveV3Base.sol), [Aave governance](https://governance.aave.com/), and the verified contracts linked by the address book. This review performed no live chain reads.
4. **Economic outcome data is missing:** collect original event histories and block timestamps for positions/liquidations, underlying token supply/debt/index data, and original DEX pool/reserve/trade data. Freeze/pause transitions and parameter changes are necessary to avoid attributing governance changes to market moves.
5. **Security and incident evidence is missing:** collect implementation-matched audits, formal verification assumptions, remediation commits and original incident postmortems, including adapter parameter incidents. Starting indexes: [Aave security](https://aave.com/security) and [Aave Price Feeds security directory](https://github.com/aave-dao/aave-price-feeds/tree/00d0f14b0734dc6faf41960bb9023c0b742a944b/security). Audit existence alone does not establish coverage.
6. **Asset dependencies are missing:** collect underlying stablecoin issuer redemption/reserve disclosures; collateral wrapping, staking and redemption contracts; Base/OP Stack sequencer, finality and bridge documentation; and each actual Chainlink feed's specification. These determine whether nominal collateral value can be realized and whether data remains usable under stress.

No application risk engine, provider, endpoint, or final scoring formula was changed or designed.
